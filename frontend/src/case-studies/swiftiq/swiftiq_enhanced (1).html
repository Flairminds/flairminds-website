AML · Sanctions Screening · SWIFT Compliance
● SYSTEM OPERATIONAL

What problem are we solving?

Banks and financial institutions send millions of payment instructions daily using SWIFT — a global messaging network. Regulators require every institution to screen these messages for money laundering, sanctions violations, and financial crime before processing them. Failure to screen correctly leads to billion-dollar fines, licence revocations, and criminal liability for compliance officers.

Existing vendor solutions (Actimize, Fircosoft, Oracle FCCM) cost $500k–$2M per year in licensing. They are black boxes — no transparency into why a transaction was flagged. And they require sending transaction data to external servers, creating data residency violations under GDPR and MAS TRM.

SwiftIQ Guard solves this by being open-stack, on-premise, and fully explainable.

Planning decisions made

Must-have requirements
Screen MT103 (payments), MT700 (trade finance), MX pain.001 (ISO 20022). Flag structuring, sanctions, high-risk corridors, TBML. Generate readable audit narratives. Role-based access for compliance teams. Full immutable audit trail.
Non-negotiable constraints
Zero transaction data leaves the institution's network. AI narrative generation must be on-premise. Supabase for audit storage. Sub-3-second end-to-end screening. Cost must be near-zero in infrastructure per message.
Why 4 tiers?
No single method catches all financial crime. Rules catch known patterns fast. ML catches novel patterns probabilistically. Fuzzy matching catches sanctions evasion via name variants. AI synthesises it all into an auditable explanation.
Why local Llama 3.1?
Sending transaction details to OpenAI or Anthropic APIs would violate banking data residency policies. Llama 3.1 on Ollama runs on the institution's own GPU server — data never leaves the network boundary.

Stack decisions and why

React + Vite + Tailwind
Fast hot reload for development. Small production bundle. Tailwind gives consistent design tokens without a component library. Vite's native ESM means no Webpack config complexity.
Vanilla JS parsers
SWIFT MT format is proprietary — no reliable open-source parser exists in JavaScript. We wrote our own using regex block extraction and field tokenisation. This keeps parsing in-browser with zero network cost.
Python Flask sidecar
ML libraries (XGBoost, scikit-learn) are Python-native. Flask is the lightest way to expose them over HTTP. Running as a sidecar means it can be scaled independently from the frontend without refactoring the main app.
XGBoost + Isolation Forest
XGBoost is the industry standard for tabular classification — trained on 50k SWIFT message feature vectors. Isolation Forest is unsupervised, requiring no labelled anomaly data, which is rare in compliance datasets.
Supabase / PostgreSQL
Managed PostgreSQL with row-level security. Insert-only audit table enforced at the database policy level — even an admin SQL query cannot delete an audit entry. Built-in REST API for integration.
Llama 3.1 via Ollama
8B parameter model runs on a single GPU server. Produces professional 2-4 sentence audit narratives from a structured prompt. Deterministic at temperature 0.2 — same input reliably produces the same style output.

How data flows through the system

1
Input
Officer pastes raw SWIFT text or uploads a batch file into the interface.
2
Parse
JS parser converts raw text → structured JSON (fields, amount, parties, HS codes).
3
Tier 1 — Rule Engine
Checks amount thresholds, country corridors, HS code lists → returns flags + risk level.
4
Tier 2 — ML Models
Feature vector sent to Flask → XGBoost returns probability + class, Isolation Forest returns anomaly score.
5
Tier 3 — Sanctions Screening
Party names screened against OFAC/EU/UN via Levenshtein fuzzy match → returns match or clear.
6
Tier 4 — Safe-Path Consensus + AI Narrative
Safe-Path takes max severity across all tiers → Llama 3.1 generates narrative → result stored in Supabase.
7
Queue
If HIGH or CRITICAL → case enters compliance queue for officer review.
8
Action
Officer clears/blocks/escalates → action written to immutable audit log.

External parties (subjects of screening, not system users)

Ordering customers
The entity sending the payment — extracted from field :50: in MT messages. Their name is screened against sanctions lists. Their country is checked against the corridor risk registry. Their transaction history is fed to the Isolation Forest anomaly model.
Beneficiaries
The entity receiving the payment — extracted from field :59:. Subject to the same sanctions screening as the ordering customer. The combination of originating and destination country determines the corridor risk score fed to XGBoost.

Risk levels — what they mean and what triggers them

CRITICAL
Transaction is immediately escalated. Processing must stop.
Triggered by: confirmed sanctions hit (OFAC/EU/UN match ≥80% similarity) · payment involving a sanctioned country with no OFAC licence · dual-use goods (TBML) in an MT700 to a high-risk jurisdiction · ordering or beneficiary country on FATF blacklist · explicit override when rule engine finds CRITICAL and overrides LOW ML score via Safe-Path
HIGH
Case enters compliance queue. Officer review required before processing.
Triggered by: structuring (amount $9,000–$9,999 just below $10,000 CTR threshold) · payment to a FATF grey-list country · XGBoost probability above 70% · Isolation Forest anomaly flag · counterparty account age under 30 days with high transaction frequency · transaction frequency 7x+ per week for same corridor
MEDIUM
Flagged for review but can be processed with officer note.
Triggered by: payment to a moderate-risk corridor (e.g. East Africa, Southeast Asia) with no other flags · XGBoost probability 40–70% · round-number amounts ($10,000 exactly) in combination with a medium-risk corridor · new counterparty (account age 30–90 days) with moderate frequency
LOW
No action required. Transaction is clear to process.
No flags from any tier. Amount outside structuring window. Parties not on any watchlist with similarity above 80%. Corridor is low-risk (Western Europe, US, Japan, Australia, Singapore). XGBoost probability below 40%. No Isolation Forest anomaly. No HS codes present or HS codes are non-dual-use goods.

Specific flags and what triggers each one

TBML_DUAL_USE_GOODSMT700 letter of credit contains an HS code from the dual-use goods registry. Example codes: 8543.70 (electronic integrated circuits), 2903.7 (halogenated hydrocarbons — precursor chemicals), 8803 (parts for aircraft). These are goods with civilian and military applications, commonly used in invoice manipulation to move money across borders under the cover of legitimate trade.
HIGH_RISK_CORRIDORThe ordering country or beneficiary country is on the FATF blacklist or is a US-sanctioned jurisdiction. Current examples: Iran, North Korea, Syria, Cuba, Russia (certain sectors), Belarus. A payment from Frankfurt to Tehran triggers this flag regardless of amount, regardless of what the ML model says, and regardless of who the named parties are.
SANCTIONS_HITA party name from :50: or :59: matches an entity on the OFAC SDN list, EU Consolidated Sanctions list, or UN Security Council list with Levenshtein similarity of 80% or above. The 80% threshold catches deliberate typos and transliteration variants — "TEHRAN IMPORT EXPORT CO" matches "TEHERAN IMPORT EXPORT CO" at 92%.
STRUCTURING_ALERTTransaction amount falls within $500 below a regulatory reporting threshold. In the US this threshold is $10,000 (Currency Transaction Report). So amounts of $9,500–$9,999 trigger this flag. The pattern — deliberately keeping transactions just below the threshold to avoid CTR filing — is one of the most common money laundering techniques. The $500 window is configurable per jurisdiction.
BEHAVIORAL_ANOMALYIsolation Forest detected that this transaction's feature profile is a statistical outlier compared to the historical baseline for similar transactions. Common triggers: a counterparty active for only 15 days but already processing 8+ transactions per week, or an unusually large amount for a corridor where the historical average is much lower. This catches novel patterns that no predefined rule would catch.
ROUND_NUMBER_SUSPICIOUSAmount is an exact round number ($50,000.00, $100,000.00) combined with a medium or high risk corridor. Round numbers alone are not suspicious — round numbers plus a risky corridor suggest the amount was chosen for convenience rather than corresponding to a real commercial invoice, which is a TBML indicator.
NEW_COUNTERPARTY_HIGH_FREQThe beneficiary account is less than 90 days old but is already appearing in multiple transactions per week. Freshly created accounts used immediately at high frequency is a common money mule and shell company pattern.

The Safe-Path override rule

Why the highest severity always wins
When Tier 1 finds a CRITICAL flag (e.g. TBML dual-use goods) but Tier 2 ML model scores the transaction as LOW risk (because the ML model has never seen this exact pattern), the consensus engine does NOT average them. It takes the maximum severity — CRITICAL wins. This is intentional. The cost of a false negative (missing real financial crime) is billions in fines and criminal prosecution. The cost of a false positive (flagging a clean transaction) is an officer spends 5 minutes reviewing it. The asymmetry of consequences justifies always taking the conservative path.

Testing pyramid — what each layer does

F
Fixtures — shared data, not tests
Real SWIFT message strings (MT103 clean, MT103 structuring, MT103 high-risk corridor, MT700 TBML, MX pain.001), fake watchlists (OFAC/EU/UN), and ML feature vectors. Every test file imports from here so test data is consistent and maintained in one place.
U
Unit tests (55 tests) — individual functions in isolation
No servers, no database, no browser. Tests the MT/MX parsers, rule engine (structuring, TBML, corridors, clean), fuzzy matcher (exact, typo variants, true negatives, multi-list), Safe-Path consensus (override scenarios), and RBAC (permissions per role, JWT validation). 55/55 passing.
I
Integration tests (29 tests) — services wired together
Requires Flask ML running and Supabase mock active. Tests Flask /classify, /anomaly, /health endpoints with real HTTP. Tests the full 4-tier pipeline from raw message to AI narrative. Tests case persistence, audit trail immutability (DELETE returns 403), RBAC enforcement on API routes. 29/29 passing.
E
E2E tests (21 pass, 5 skip) — real browser, real user flows
Playwright opens Chromium, logs in, pastes SWIFT messages, clicks screen, verifies risk badge appears, verifies case enters queue, officer clears it, audit log records the action. 5 skips are for unbuilt features (batch UI, audit search). 0 failures.
P
Performance tests (not run yet) — production SLA validation
k6 runs 6 scenarios: baseline (5 users, 1 min), ramp-up (to 50 users), spike (sudden 100 users), batch load, ML microservice isolation, 10-minute soak. Pass criteria: P95 pipeline under 3,000ms, Flask ML under 500ms, error rate under 1%.

Deployment plan — step by step

1
Infrastructure setup: Provision a Linux server (Ubuntu 22.04). Install Node 20, Python 3.11, Ollama. Pull the llama3.1 model locally. Configure firewall — only ports 443 (HTTPS), 5001 (Flask, internal only), 11434 (Ollama, internal only).
2
Environment variables: Set OLLAMA_BASE_URL, SUPABASE_URL, SUPABASE_ANON_KEY, JWT_SECRET in a server-side .env file. Never commit these to git. Add to GitHub Secrets for CI/CD pipeline.
3
Database setup: Connect live Supabase project. Run schema migrations — create cases table, audit_log table with INSERT-only RLS policy, users table. Seed the watchlist tables with OFAC/EU/UN data.
4
Flask ML sidecar: Deploy as a systemd service on the same server. Start with: systemctl enable swiftiq-ml. Verify /health returns models_loaded: true. The XGBoost and Isolation Forest models load from the 50k training CSV at startup.
5
Vite production build: Run npm run build. Output goes to /dist. Serve with Nginx as a static SPA. Configure Nginx to proxy /api/* requests to the backend and /ml/* to Flask on port 5001.
6
CI/CD pipeline: GitHub Actions runs Unit → Integration → E2E → Build on every push to main. Performance tests run on a weekly schedule. A failed test blocks the deployment automatically.
7
Staging sign-off: Compliance team runs 20–30 real historical SWIFT messages through staging. Compares results to known outcomes. Signs off that the risk engine correctly categorises their test set before production switch.
8
Production go-live: DNS cutover. Monitor error rate and latency for 48 hours. Flask ML and Ollama health checks run every 60 seconds — alert via Slack if either goes down.
